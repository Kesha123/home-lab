# ci-lab VM — Woodpecker CI

Woodpecker CI server + agent, backed by PostgreSQL (TLS) and fronted by nginx, deployed on the `ci-lab` libvirt VM. Reverse-proxied by Caddy on the host server. Forge: Codeberg (Gitea-compatible).

## Networking

The VM has two NICs:

| Interface | Type | IP | Purpose |
|---|---|---|---|
| eth0 | virbr0 (NAT) | 192.168.122.10 | Host → VM (Caddy reverse proxy → nginx:80) |
| eth1 | macvtap (enp1s0) | 192.168.0.253 | Laptop → VM (SSH, ansible) |

**macvtap limitation:** the host server cannot reach 192.168.0.253 — only other machines on the physical LAN (e.g. laptop) can. This is why Caddy proxies to 192.168.122.10 (virbr0), while ansible/SSH uses 192.168.0.253 (macvtap).

## Prerequisites

### 1. Codeberg OAuth application

Register an OAuth2 app on Codeberg:

1. Log into `https://codeberg.org`
2. **Settings → Applications → OAuth2 Applications → Create new**
3. **Application name:** `Woodpecker CI (ci-lab)`
4. **Redirect URI:** `https://ci-lab.innokentii-kozlov.com/authorize`
5. Copy **Client ID** and **Client Secret**

### 2. Zot API key

Generate an API key for `zot.innokentii-kozlov.com`:

1. Log into `https://zot.innokentii-kozlov.com` (via Authentik OIDC)
2. User settings → generate API key
3. Note the username (email/subject used to log in)

### 3. secrets.yaml

Create `vms/ci-lab/secrets.yaml` (gitignored). Example:

```yaml
woodpecker_admin: <your-codeberg-username>
woodpecker_gitea_client: <codeberg-oauth-client-id>
woodpecker_gitea_secret: <codeberg-oauth-client-secret>
zot_username: <zot-username>
zot_api_key: <zot-api-key>
```

## Generated .env

The deploy workflow auto-generates `.env` on the VM at `~/stack/.env`. Structure:

```env
WOODPECKER_HOST=https://ci-lab.innokentii-kozlov.com
WOODPECKER_ADMIN=<your-codeberg-username>
WOODPECKER_GITEA_CLIENT=<codeberg-oauth-client-id>
WOODPECKER_GITEA_SECRET=<codeberg-oauth-client-secret>
WOODPECKER_AGENT_SECRET=<openssl-rand-hex-32>
WOODPECKER_PROMETHEUS_AUTH_TOKEN=<openssl-rand-hex-32>
POSTGRES_PASSWORD=<openssl-rand-hex-32>
```

`WOODPECKER_AGENT_SECRET`, `WOODPECKER_PROMETHEUS_AUTH_TOKEN`, and `POSTGRES_PASSWORD` are generated by the workflow and persisted in `target/ci-lab/generated-secrets.yaml`.

## Deployment

### 1. Build & start VM (first time only)

```bash
cd vms
make build/cloud-init/ci-lab
make copy/cloud-init/ci-lab
make start/ci-lab
```

### 2. Package stack as OCI artifact

```bash
cd vms
make package/ci-lab
```

Builds an OCI artifact containing `compose.yaml`, `nginx/nginx.conf`, `postgres/init.sql` and pushes it to the zot registry.

### 3. Deploy

```bash
cd vms
make deploy/ci-lab
```

Runs the ansible workflow from a container on the laptop:

1. Reads `secrets.yaml` (localhost)
2. Generates secrets (localhost)
3. Pulls OCI artifact from zot → `~/stack/` (ci-lab)
4. Generates self-signed CA + postgres TLS certs (ci-lab)
5. Renders `.env` + writes `~/.docker/config.json` (ci-lab)
6. Runs `docker compose up -d` (ci-lab)

## Prometheus metrics — manual step

> **Security warning:** the following puts the Woodpecker metrics scrape token in the git repository. Anyone with repo access can read Woodpecker metrics (pipeline counts, repo names, user counts). This is acceptable for a homelab but **do NOT do this in production**.

After deploying, copy the `WOODPECKER_PROMETHEUS_AUTH_TOKEN` value from `~/stack/.env` on the ci-lab VM:

```bash
ssh admin@192.168.0.253 'grep WOODPECKER_PROMETHEUS_AUTH_TOKEN ~/stack/.env'
```

Paste it into `stack/config/monitoring/prometheus/prometheus.yml`, replacing `<PASTE_FROM_CI_LAB_ENV>`:

```yaml
  - job_name: "woodpecker"
    metrics_path: "/metrics"
    scheme: "https"
    bearer_token: '<paste-token-here>'
    static_configs:
      - targets: [ci-lab.innokentii-kozlov.com]
```

Then sync to the server and restart Prometheus:

```bash
cd stack
make stack/sync/systemd-unit-config/all
ssh admin@dell-optiplex-3000.innokentii-kozlov.com 'systemctl --user restart prometheus'
```
